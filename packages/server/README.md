# @pi-superagent/server

Persistent single-administrator Super-agent service using Pi SDK 1.5.0. One instance can coordinate an application workspace containing multiple cooperating Git repositories. Includes the `pi-superagent` CLI and bundled Web UI.

Runs locally or on a Linux SSH host controlled from the user's local Pi. GitHub is an optional channel, not an installation or task prerequisite. Unconfigured GitHub tools and publication prompts are not exposed to agents.

Requires Node.js 24+ and Git. Version `0.1.0-alpha.1` is under development; the npm scope must be confirmed before publication.

```sh
pi-superagent init --repo /absolute/repository --state-dir /absolute/instance
pi-superagent serve --state-dir /absolute/instance
```

Open `http://127.0.0.1:4317` directly. New instances default to local mode and do not create or require an administrator token. Configure both `routerModel` and `workerModel` through the Web panel. Supply model credentials through `INSTANCE/agent/auth.json`, `INSTANCE/agent/models.json`, or explicit provider environment variables when starting the service. No personal Pi configuration is automatically imported. Agent HOME/config directories are under INSTANCE/agent/home; background jobs receive only basic runtime and proxy/CA environment, not provider, GitHub or administrator credentials. Direct gh jobs are rejected: replies must go through Router/Outbox. Configure build tools and Git credentials in the instance home. Personal SSH identities are not automatically selected.

Local mode trusts processes on this machine and binds only to 127.0.0.1. API writes require `Content-Type: application/json` and `X-Superagent-Local: 1`; Host/Origin checks remain enabled. Use `init --management token` for authenticated management and protect the instance directory with account-specific permissions. Older instances without `management.json` retain token mode. Change modes offline with `management local|token --state-dir INSTANCE`, or use Pi `/superagent local` to confirm a graceful conversion and restart. Management mode is independent of model authentication, GitHub PATs and SQLite business settings.

Use `discover --repo ROOT` to inspect a workspace without changing it. Initialize it with `init --workspace --repo ROOT --state-dir INSTANCE --paused --max-workers 1`; repeat `--member RELATIVE_PATH` to select members explicitly. INSTANCE must be outside ROOT. Member identities and paths are fixed after initialization. Each ticket pins member HEADs, assembles independent worktrees at the original relative paths, and retains per-repository results. Missing modules are not fetched; source uncommitted files are not copied. `workspace [TICKET_ID]` and the Web workspace/results views expose members, baselines and checks. Existing single-repository instances remain compatible.

For SSH management, preinstall this package, Node 24+ and Git on the Linux host and prepare an existing checkout. In local Pi, run `/superagent ssh` and supply the host alias, remote Node executable and this package's absolute `dist/cli.js` path. The adjacent `remote-child.js` provides a bounded stdio control protocol; it is not a public HTTP endpoint. Remote instances require token mode; new SSH instances are paused with one Worker. Local SSH forwarding uses the same port as the remote API, preserving exact Host/Origin checks. `/superagent models` runs the SDK login on the remote host while keeping private input in local Pi. Disconnecting Pi or SSH does not stop the background service, whether detached or systemd-managed. No automatic package installation or code synchronization is performed.

For a fresh machine, the unified release bundle provides `node install.mjs --yes`: native Node/npm installation of both packages, a matching Pi entry with a private profile, and a CLI entry. No source build, WSL, global PATH changes or implicit service start. Node 24+/npm 10+ and Git 2.31+ are prerequisites. See the project’s `docs/installation.md`; existing npm/source workflows remain available.

`pi-superagent --help` lists request, followup, status, stop, retry, pause/resume, start, shutdown, service management, doctor, and `backup DEST`, `backup-check BACKUP`, `restore BACKUP`, `backup-prune ROOT --keep N` commands. Linux systemd 245+ supports `service plan|status|install|enable|disable|uninstall`; mutations require `--yes`. Install/uninstall require an offline instance; install does not start or enable, and enable/disable do not start/stop. Registered start/shutdown use systemctl; bare serve is refused. Use `/superagent service` for confirmed local/SSH control. The unit uses env-i and private `service.env.json` for proxy/CA/PATH, with credentials in instance files; it does not inherit shell credentials. Login autostart is separate from administrator-enabled linger for boot without login. Use `--id` for idempotent request/followup retries. An accepted request is not a completed task.

Backups are verified offline snapshots containing credentials, sessions, SQLite and work files. Stop the instance and disable registered supervision first. Restore requires `--expected-instance-id UUID`, the original absent path and matching host/account/Git dependencies; restore and pruning preview unless `--yes` is supplied. Restore preserves identity and pause state without starting or registering the service. Keep external Git storage/administration backups separately. Cross-host/path/schema migration and automatic business-data cleanup are not included. See the project’s `docs/backup.md` for upgrade/rollback and retention steps.

The service owns SQLite, effect retries and role-bound child processes. Workers get an isolated single- or multi-repository worktree workspace and persistent Session, managed background jobs, and report/handback tools. They run with the service account's operating-system privileges; deploy using a dedicated restricted account or isolated environment.

Single-repository instances support GitHub through the Web Sources page: configure one repository, botLogin and allowedActors; supply a dedicated machine-account PAT in INSTANCE/github.token or PI_SUPERAGENT_GITHUB_TOKEN. Requires repository Metadata/Contents/Checks/Commit statuses read and Issues/Pull requests write permissions. Polls issues, PRs, comments, reviews, CI and lifecycle; persists cursors and deduplicates replies. Git push credentials must be configured separately. When GitHub is enabled, Worker tools create/reuse draft PRs and validate ticket PR bindings; they never merge. Inferred work uses rule/direction/evidence validation and observe/auto/off modes.

CLI sources, github poll, decisions, triggers and diagnostics ID expose operational state. Web follows Overview/Source/Input/Evaluation/Execution/Settings navigation, with setup readiness, durable local conversation, live ticket details, contextual actions, linked thread history and global search. Model/concurrency/rule/team forms preserve conflicting drafts and expose settings history. Model metadata is read through a bounded, isolated fixed-SDK child; login and optional paid probes stay in Pi's explicit `/superagent models` flow. Update/rebuild, reload the Pi extension and explicitly restart the service before refreshing this panel. Real Chromium operations and local GitHub HTTP/Pi SDK integration are tested.

Current limits: Feishu is deferred by request; GitHub App installation tokens and Enterprise endpoints are not supported. Live GitHub read-only model work, bot replies and restart deduplication have been verified; live push/PR lifecycle remains outstanding. Multi-repository instances currently use manual requests; multi-repository GitHub/PR, native GitLab Issue/MR channels and in-place execution are not connected. GitLab-hosted repositories can already be used as local checkouts with manual Pi/Web requests; no GitHub account or repository migration is needed. Full upstream prompt/skill override editing and DSH-specific executor features remain to be adapted. Unregistered start remains detached. Systemd unit syntax and real launcher process-crash/persistence recovery have been tested without host registration; real user-manager auto-restart/boot and launchd/Windows supervision remain outstanding. Linux is locally verified; macOS/Windows and interactive Pi TUI acceptance remain outstanding. Data is retained on uninstall.

Dependency audit (2026-11-05): Pi SDK 1.5.0 uses patched minimatch 11.0.3 and undici 8.12.3; Zod remains pinned to 4.6.7. Public npm production audits returned zero findings for the workspace and clean-installed tarballs, without root overrides. Run the workspace's `npm run test:security` after building to repeat both audits and package checks. Existing services load the new SDK only after updating dependencies and explicitly restarting; update the remote package too for SSH instances.

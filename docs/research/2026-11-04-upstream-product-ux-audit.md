# 与 dsh-superagent-prototype 的产品及交互对照

## 范围与结论

本轮只审查，不修改产品代码或用户实例。

- 公开仓库：`https://github.com/deepseek-ai/dsh-superagent-prototype`。
- 本次查询的远端 HEAD：`8c32a9dc5d72c033816c6a8110b37f40cf94fba4`，另克隆到临时目录检查，未更新 `upstream/`。
- 本地参考提交：`6337fc823ce20251c8de8085948165c81aaa701e`。排除 `.git` 后，两份仓库文件内容一致；本产品 `packages/server/src/core/` 也与上游 core 一致。
- 方法：阅读 README、SETUP、Philosophy/Execution/Panel 规范，对照上游 React 面板、API 及当前 Pi 插件/Web/运行适配层。没有运行 DSH 实例。

**结论：领域核心相同，运行宿主已适配，但功能与产品体验不是完整等价移植。当前前端是另写的简化管理壳，缺少上游已有的多项交互；新增本地派单还缺少完整的本地消息渠道体验。**

上游的核心产品要求是“尽量少占用人的注意力”，面板依次回答：现在是否需要我、系统是否正常、某件事从输入到工单如何发展。当前实现优先打通 API 和持久化，没有把整条用户流程作为同等重要的交付目标。

## 能力对照

| 范围 | 上游 | 当前实现 |
| --- | --- | --- |
| 领域模型 | Trigger/Decision/Ticket/Mandate/Assignment/Subscription | core 文件保持一致 |
| 执行宿主 | DSH Session、preset、后台任务及子 Agent 生命周期 | Pi SDK 独立进程、Jobs、持久投递；属于重新适配，非执行特性逐项等价 |
| 使用入口 | GitHub/飞书原会话发请求和收回复，Web 监督，能打开主/Worker Session | Pi 命令、CLI、独立 Web；增加本地请求入口，但没有等价的用户消息流 |
| 仓库/来源 | 单 GitHub 仓库，GitHub 与可选飞书 | 增加多仓库本地工作区；单仓库 GitHub 保留；飞书按要求延期 |
| 状态与导航 | 部署问题、暂停、任务阶段、Thread 时间线及互相跳转 | 待处理、简单工单列表和通用记录页；缺完整就绪状态和关联导航 |
| 设置 | 分组表单、模型目录候选、草稿/冲突处理、保存历史、提示词预览/差异 | 团队约定/GitHub 有表单；其余主要完整 JSON；历史留在后端但无相应用户界面，提示词管理未完整移植 |

## 具体发现

### P0：未配置完成却呈现正常空状态

- 上游 `upstream/src/client/overview.tsx` 将 setup、executor-paused 等列为可操作问题，并跳转设置或提供恢复操作。
- 当前 `packages/server/src/attention.ts` 主要统计工单人工事项、失败评估与重试错误，未把缺少模型或初始配置未完成纳入就绪问题。
- `packages/server/web/app.js` 的 `loadAttention()` 因而可以显示“暂无需要你处理的事项”，同时实例仍无模型、不能处理任务。
- 最近提交修复在表单附近加了提示，但首页、初始化结束状态和服务运行状态仍没有统一。

### P0：本地回复没有正常的消息阅读路径

- 上游通过原 GitHub/飞书会话交付回复，面板提供原会话和 Session 链接：`upstream/src/client/ticket.tsx`、`app.tsx`、`index.tsx`。
- 当前 `packages/server/src/runtime.ts` 的 reply effect 对 manual 渠道标记 `sent` 并持久化/写审计。
- 当前 Web 没有按本地请求/工单呈现这些 Router 回复的消息流。数据能从审计或结构化工单中查到，用户却没有相当于“原会话”的阅读入口。
- 最近增加的请求回执解决了是否收件，不等于完成请求、回复、追问、结果的阅读链路。

### P1：工单列表更新，但打开的详情不会自动更新

- 上游 `TicketPage` 用 `usePoll()` 持续更新详情。
- 当前 `refresh()` 只刷新列表；`detail(id)` 仅在点击或部分操作后调用。`selected` 被赋值，但没有用于轮询详情。
- 因此用户可能看到列表状态已变，而详情仍是旧状态或旧问题。

### P1：模型与日常设置仍像内部调试入口

- 上游 `settings-kit.tsx/ModelField` 使用模型目录，支持 provider/model/reasoningEffort 候选和默认模型说明。
- 当前 Web 将 `routerModel/workerModel` 放进完整 JSON 编辑器，无法在面板完成常规的型号选择与角色配置。Pi 向导提供了初始共同型号选择，但不是独立的日常设置入口。
- 上游 `draft.tsx` 有草稿状态、可见保存栏、并发版本合并/冲突说明；当前有 revision 拒绝覆盖，但没有相应的用户解决流程。

### P1：插件菜单主要把 API 响应直接显示给用户

- `packages/extension/src/index.ts` 中状态、工单和提交结果大多通过 `JSON.stringify(..., null, 2)` 写入通知。
- 用户需要理解内部 ID、状态及结构，才能决定下一步，缺少正常任务摘要和选择操作。
- `setup.ts` 将“继续配置”放在“创建或继续”分支；“连接已有实例”只连接，不补模型。已有实例的模型调整还要经过工作区选择/成员核对等初始流程。

### P1：操作与当前状态不匹配

- 上游 `ticket.tsx` 按 `data.actions.retry/stop` 决定操作是否可见。
- 当前 `detail()` 总是添加停止和重试按钮，再由 API 拒绝不适用操作。用户必须通过错误来发现按钮不能用。

### P2：配置、历史和信息组织有明确缺项

- 上游有 Thread→Trigger→Decision→Ticket 的关联导航，以及跨输入/会话/工单的全局搜索；当前主要是工单标题/ID 搜索和通用记录 JSON。
- 上游有提示词完整预览、版本差异、默认值升级提醒及设置历史；当前未完整移植。
- 本地工作区仍保留较显眼的禁用 GitHub 表单和飞书延期说明，分散当前流程的注意力。
- `setup.ts` 的成功通知仍包含“一键打开并登录 / 查看复制管理员令牌”，没有随本地免登录模式统一更新；菜单离线时也不能准确沿用本地模式信息。这是多个入口分别追加功能造成的一致性缺口。

## 应采用的调整方向

保留领域核心、Pi 执行适配与多仓库能力，以原型现有面板交互为基线整理产品层，而非继续向简化页面零散追加按钮。

优先完成同一条用户流程：

1. 打开应用即可知道未配置、可派单、暂停或故障，以及唯一明确的下一步。
2. 在清晰的模型/执行设置中完成配置；已有实例无需重复走创建流程。
3. 提交后的请求立即可见，并能连续查看接单、处理、追问、人工回答和结果；补齐本地消息渠道。
4. 详情持续更新，按钮仅对应当前可用动作；普通结果不藏在原始 JSON 或日志里。
5. Pi 插件提供简明状态、任务选择和 Web 入口；诊断、原始记录、凭据与高级来源设置放入次级入口。
6. 在上述流程成立后补齐设置草稿/历史、提示词管理和全局检索。

这是一轮产品层对齐，需要共同的状态模型和交互组件；只调整配色或再加几条提示无法解决这些流程断点。
